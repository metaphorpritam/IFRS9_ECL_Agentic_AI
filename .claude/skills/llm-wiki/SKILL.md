# llm-wiki — compile knowledge, link it, remember it, audit it

The pattern (Karpathy's LLM wiki — gist `karpathy/442a6bf...94f` — adapted
for a repo + docs): instead of
retrieving from raw sources on every question, **compile** the sources once
into small, interlinked, LLM-maintained Markdown pages — then answer from the
wiki, and file every new insight back into it. Knowledge compounds; raw files
get read once, not every session.

Four concerns, one directory:

1. **Graph** — pages carry typed links in frontmatter plus `[[wikilinks]]` in
   the body; `wiki_graph.py` compiles them into `.wiki/graph.json` (nodes,
   typed edges, unresolved links). Vectorless: retrieval is reasoning over a
   graph, not embedding similarity.
2. **Memory** — `memory/log.md`, `decisions.md`, `questions.md` are
   append-only and cheap to read. Together with `index.md` they are the
   compaction-recovery ritual (below).
3. **Query** — `wiki_query.py` turns a question into an ordered, explainable
   reading list (lexical seeds + k-hop expansion). You read the pages, answer
   with `page.md#Heading` citations, and file the answer back.
4. **Audit** — `wiki_audit.py` proves the wiki is healthy: broken links,
   orphans, **stale pages** (source hashes vs the manifest), uncovered
   sources, TODOs, duplicates. Errors exit 1.

All scripts are stdlib-only with PEP-723 headers (`uv run` or plain
`python`), UTF-8 on every file operation, Windows-safe paths, and **no silent
skips** — every ignored line, unreadable file, and unresolved link is printed
with a reason.

## Layout

```
wiki/
├── index.md                  map of content (LLM-maintained, always current)
├── pages/*.md                one page per concept/module/entity/decision/...
├── memory/log.md             session journal        (append via wiki_log.py)
├── memory/decisions.md       decision records
├── memory/questions.md       open questions
└── .wiki/
    ├── config.json           source roots + code globs (audit scope)
    ├── graph.json             generated by wiki_graph.py
    ├── source_manifest.json   hashes recorded by wiki_audit.py --update-manifest
    └── audit.json             latest audit report
```

The wiki is Obsidian-native (open it as a vault for the graph view and
backlinks) and is just files — keep it in git. Page anatomy, edge types,
and the exact frontmatter grammar the parser accepts are in
`references/schema.md` — **read it before writing your first
page**; the parser reports lines it can't understand rather than guessing.

## Workflow

Replace `SKILL_DIR` with this skill's directory. `uv run` and `python` are
interchangeable here (scripts are stdlib-only).

### 0. Initialise (once per project)

```bash
python SKILL_DIR/scripts/wiki_init.py wiki --name "Pricing Service" \
    --source-root ../src --source-root ../docs --code-glob "**/*.py"
```

Put the wiki inside the project (`<project>/wiki/`); roots are stored
relative to it, so `../src` stays valid on every machine.

### 1. Compile — the agentic step (you, not a script)

Read sources and write/update pages. The discipline that makes this work is
in `references/playbook.md` (read it the first time, skim it after):
**update-don't-append**, one page per stable thing, provenance in `sources:`
/ `code:`, cross-link aggressively, keep `index.md` current. For big doc
corpora, ingest with **pageindex-plus** first and compile pages from its
corpus; for code, run its `scan_code.py` and compile module pages from the
call graph instead of re-deriving it. Two rules from the original
pattern: **raw sources are immutable** (read, never modify — the wiki is
derived, the sources are truth), and **every page gets a one-line entry
in `index.md`** — the index-first read is what replaces RAG at query
time, and the audit flags pages missing from it.

### 2. Build the graph (after every compile session)

```bash
python SKILL_DIR/scripts/wiki_graph.py wiki --print
```

Fix anything reported unresolved *now* — an unresolved link is either a typo
or a page that wants to exist.

### 3. Declare the wiki current

```bash
python SKILL_DIR/scripts/wiki_audit.py wiki --update-manifest
```

This hashes every referenced source. From here on, `wiki_audit.py wiki`
tells you exactly which pages went stale when the underlying files change.

### 4. Query loop (how questions get answered)

```bash
python SKILL_DIR/scripts/wiki_query.py wiki "how are discounts applied?" --explain
```

Read the listed pages top-down, answer citing `page.md#Heading`, then **file
the answer back**: update the page it belongs on, or record it via

```bash
python SKILL_DIR/scripts/wiki_log.py wiki decision "..." --tags pricing
```

An answer that isn't filed back is knowledge lost — the whole point is that
the second time is free.

### 5. End every session

```bash
python SKILL_DIR/scripts/wiki_log.py wiki log "what changed; what's next"
python SKILL_DIR/scripts/wiki_audit.py wiki            # must be error-free
python SKILL_DIR/scripts/wiki_audit.py wiki --update-manifest   # if you compiled
```

Every few sessions, also run the **semantic lint pass** from the playbook
— contradictions, superseded claims, missing pages/cross-links, data gaps
— the meaning-level health check the deterministic audit cannot do.

### Compaction / new-session recovery ritual

Read, in order: `wiki/index.md` → last ~3 entries of `memory/log.md` → the
counts block of `.wiki/audit.json`. That's the whole state restore — do NOT
re-read raw sources to "get oriented"; that's what the wiki is for.

## Hard rules (earned the hard way)

- **No silent skips, ever.** The scripts already log every ignored line and
  unreadable file; hold your compile work to the same bar — if you skip a
  source, say so in the log entry with the reason.
- **Verify by reading the generated artifacts**, not by assumption: after a
  compile session, open `graph.json`'s unresolved list and the audit output.
  "It probably linked" is how wikis rot.
- **Update, don't append.** Re-reading a source means revising its page in
  place (and its `sources:` anchors), not adding "Update:" paragraphs.
- **Filenames lie.** Confirm a source's identity from its first page/slide
  before compiling it into a page.
- On Windows, write helper code to `.py` files and run them (PEP-723 headers
  + `uv run`) — PowerShell heredocs mangle backslashes.

## Bundled resources

- `scripts/wiki_init.py` — scaffold wiki + config.
- `scripts/wiki_graph.py` — pages → `.wiki/graph.json` (also importable:
  `build_graph`, `parse_frontmatter`).
- `scripts/wiki_query.py` — question → explainable reading list.
- `scripts/wiki_audit.py` — health checks + `--update-manifest`.
- `scripts/wiki_log.py` — append log/decision/question entries.
- `references/schema.md` — page types, frontmatter grammar, edge semantics,
  naming rules. Read before writing pages.
- `references/playbook.md` — the compile / query / audit / memory loops with
  worked examples. Read on first use of this skill per project.
